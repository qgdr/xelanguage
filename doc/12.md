# 编译、链接与自举

本章用不要求编译器背景的方式说明 Xe 工具链。

## 从源码到程序

```text
.xe 源文件
  -> 词法与语法分析
  -> AST（源码结构）
  -> 名称解析
  -> 类型、写权限、所有权检查与指针风险 warning
  -> HIR（已经明确含义的高级中间表示）
  -> MIR（适合生成代码的简单中间表示）
  -> C 或 LLVM IR
  -> .o 对象文件
  -> 链接器
  -> 可执行程序或库
```

“对象文件”是已经翻译成机器指令、但还没有组成完整程序的文件。“链接”把各模块对象文件、
标准库和很小的运行库组合成最终程序。普通使用者只运行 `xe build`；工具会调用系统 C
编译器、LLVM 和链接器，不要求使用者手工管理参数。

## 构建目录

所有生成物放入 `target/`，不污染源码目录：

```text
target/
└── debug/
    ├── cache/       # 依赖摘要、类型接口和中间表示
    ├── deps/        # 模块对象文件
    └── hello        # 最终程序
```

内部文件包括：

- `.xmi`：Xe 模块接口，记录公开类型、Trait 实现和接口哈希；
- `.o`：平台对象文件；
- `.ll` 或 `.c`：只有调试或显式要求时保留；
- 依赖元数据：记录源文件、编译选项和依赖接口哈希。

这些格式带版本号，用户不应直接编辑。若源文件及其依赖接口哈希没有变化，模块可以复用
缓存；私有实现改变而公开接口未变时，不必重编所有下游模块。

## 编译器实现结构

宿主编译器不需要延续当前实验代码，可以重新组织为清楚的独立层：

```text
source/       文件、UTF-8、源码位置
lexer/        词法单元
parser/       语法树与错误恢复
resolve/      模块、作用域、名称
types/        类型、Trait、泛型实例
ownership/    初始化、移动、借用、析构
hir/          去除语法糖后的有类型表示
mir/          控制流、局部变量和析构点
backend_c/    便携自举后端
backend_llvm/ 高性能生产后端
build/        包图、缓存、外部工具和链接
诊断模块       所有阶段共享源码位置、错误代码与修复建议
```

第一个宿主实现建议使用 Python 和成熟解析库，数据结构使用带类型标注的 dataclass。它只需
正确实现冻结的自举子集。C 后端比自行实现机器码简单、便携，适合取得第一个 Xe 编译器；
LLVM 后端随后提供更好的优化和调试信息。

## 自举过程

1. `stage0`：宿主语言编写的参考编译器；
2. `stage0` 编译 Xe 编写的编译器源码，得到 `xec1`；
3. `xec1` 编译同一份源码，得到 `xec2`；
4. `xec2` 再编译一次得到 `xec3`；
5. 比较 `xec2` 与 `xec3` 的规范化中间表示或可复现产物；
6. 用三者运行相同的成功、失败、诊断和标准库测试。

运行库仍可以保留少量 C 代码处理进程入口、系统调用和平台 ABI；“自举”不要求操作系统
边界也完全由 Xe 实现。

## 质量要求

当前编译器检查类型、写权限和资源所有权，指针风险单独 warning；--check-safety 仅兼容旧命令。
官方自举验收记录编译器版本、语法版本和风险分析策略，不把完整区域证明当成普通指针门禁。
目标模块接口及缓存键应包含这些信息；当前尚未实现模块接口与缓存系统。

- 同一输入、工具链版本和锁文件必须产生可重复结果；
- 每个 AST/HIR/MIR 节点保留源码范围；
- 每个语言功能同时有成功测试、失败测试和诊断快照；
- 解析器对常见错误继续分析，避免只显示第一个错误；
- 自举固定点由 CI 自动验证；
- 优化器不参与语言正确性，关闭优化仍应通过全部语义测试。

前端将四种管道降低到统一的显式调用/局部绑定；分支选择降低到穷尽 Match。
处理参数绑定不引入函数栈帧，因此它内部的 return 保持外层控制流。真正的 fn 单独生成
函数及可选捕获环境，Drop 清理点不可因语法糖而丢失。捕获闭包暂未实现时给出明确诊断，
不能当成普通参数绑定执行。
