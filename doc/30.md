# 语言核心、实现闭环与自举能力审核

审核日期：2026-10-01。对象：Bootstrap Syntax 0.9、现有规范第 00—29 章、
Python stage0、C 运行库及测试。本文总结已有约定和实现证据，不引入新语法。
后续新增规定或改变旧含义必须先由用户审核；下面的建议不等于已经批准的规则。

后续进展：本章保留实现自举之前的审核快照。首个 Xe 子集编译器与三代自编译链现已
实现，最新证据及限制见 [第 31 章](31.md)；下文“尚未自举”描述的是本次实现前的状态，
完整目标语言目前仍未全部移植。
原版 stage0 的统一工具入口、整程序 C 编译缓存、保守 fmt 与 API 清单也已实现，
当前命令和限制见 [第 32 章](32.md)；下面工具表保留审核时的旧状态。

## 结论先行

1. 核心语法有明确的解析与类型规则，可以组成真正运行的程序；目前没有发现需要推翻
   核心符号体系的冲突，但这不是形式化的全语言无歧义证明。
2. 语言设计、解析支持、语义支持、后端运行不是同一状态。完整目标语言尚未闭环，
   不能把冻结版本号或示例全部通过理解为规范全部实现。
3. 已有能力足以开始写 Xe 版的编译器子集；还没有 Xe 编译器源码与自编译阶段链，
   因此尚未自举。不要以继续添加高级功能替代这一缺失的工程成果。
4. “像 OCaml 一样优雅、比 Rust 易懂、像 C/C++ 足够底层”目前是三个评测目标，
   不是已经证明的整体优势。它们也存在取舍：少做静态地址证明，会增加运行时责任。

## 一组能组合的核心规则

| 核心 | 对应关系 | 读者必须知道的边界 |
| --- | --- | --- |
| 类型与地址 | `a: T`，`a@: T@`；`p: T@`，`p#: T` | 解引用能访问对象，不能取得非 Copy 对象的拥有权 |
| 访问权限 | `T@[mut]` 可写，`T@` 只读 | 可写指针可以降为只读；地址别名仍合法；只读不表示对象绝不会被别名修改 |
| 风险附件 | `T@[unsafe]` 传播地址风险 | 不改变类型身份、ABI、写权限或资源归属；没有 warning 不等于安全 |
| 复制与资源传递 | Copy 用 `=`，非 Copy 用 `<<`，`>>` 通用转送 | `>>` 不是 `<<` 的严格反向操作；普通参数/返回也会按类型复制或移动 |
| 块与退出 | `;` 丢弃表达式值，块尾表达式交付值 | 块控制语句允许省略尾分号；正常退出清理资源，panic 不保证 Drop |
| 组合与分解 | `T?[E]` 构造两分支类型，值 `?` 分流一层 | E 可以不是错误；只有返回位置允许相应成功值简写，不是任意隐式转换 |
| 调用与管道 | `f(x)`、`x \|> f`、`1> f`、`Variant :> f` 调用处理函数 | 处理参数绑定立即执行；返回函数需显式绑定；真正匿名函数用 `fn` |
| 复合表示 | `Variant[x]`、`tuple[x, y]`、`.field = x;` | 变体负载、元组和结构体初始化分别有明确入口 |
| 泛型 | `fn[T] f` 声明未知量，`f[i32]` 代入 | 声明与应用不是同一操作；具体实例有独立检查和布局 |
| 迭代 | 容器遍历绑定元素指针，`Step[T]` 绑定产生的 T | `Stop` 结束，`Item[None]` 是元素；T 本身为指针时不额外取地址 |

这里的“像公式一样可推导”是局部规则明确，不是所有符号都只有一个无上下文含义。
`:` 在值声明标类型，在泛型附件标能力约束；`?` 在类型和值位置分别构造与消解；
`[]` 在不同入口附带类型参数、负载、捕获、索引或运算附件。上下文允许确定解释，
但初学者仍需辨认这些入口，不能把词法上的相似直接说成没有认知负担。

### 已明确、不能再偷偷换含义的便利规则

- `p.field` / `p[index]` 可以越过一层普通指针；这不允许从指针移走资源。
- 方法按声明的 self 自动取得地址或 Copy 副本；非 Copy 的按值 self 不能通过指针调用。
  普通函数参数，包括格式化参数，不自动取地址。
- `fn[x@]` 保存地址，正文的 x 仍是原类型 T 的非拥有别名，不变成 T@。
  原本 `p: T@` 按值捕获后仍是 T@；这一点与隐藏环境字段类型分开。
- 捕获闭包 `f()` 沿用方法式接收者；读取/修改环境保留自己，移出捕获资源才消耗自己。
  把闭包作为另一个函数的普通按值实参，仍遵守移动规则。
- `a[i]` 的类型是元素 T，不是自动生成的 T@；`a[i]@` 才是取地址。
  非 Copy 元素不能从下标直接移出，Vec 用 pop 取得拥有元素。
- `object.f()` 按方法解析；调用函数类型字段应写 `(object.f)(x)`。
  这是当前一致的解析边界，不依据字段和方法同名与否猜测。
- 已定型变量不被上下文换类型。未定型字面量可以按预期类型定型，可写指针可以浅层降权；
  返回结果的成功包装和泛型推导各有自己的明确入口。

## 规定与实现逐项核对

“已运行”表示已有真实 C 编译/执行回归，不表示支持该领域所有可能组合。
“目标/部分”意味着不能作为用户今天可执行的完整接口。具体契约以相应章节为准。

| 功能组 | 当前实现 | 未闭合的边界 |
| --- | --- | --- |
| 词法、名称、字面量、注释 | UTF-8、嵌套注释、最长符号、源码位置与 AST JSON | 解析多错误恢复未实现，当前遇首个语法错误停止 |
| 类型与绑定 | 标量、类型分组、透明别名、let/let[mut]、只读参数 | 泛型/局部别名未设计；模块级只读 let 后端仅字面量及一元正负号 |
| 函数与控制流 | 递归、实参求值顺序、块、if/while/for、提前退出 | 没有通用重载或用户运算符重载；首版循环返回 Unit |
| 数值与布尔 | 短路、比较链、上下文常量、无损 as、整数 try_from | 浮点余数、用户聚合类型比较不支持；更完整溢出/浮点转换策略仍需确认 |
| 结构体、枚举、元组 | 创建、字段、方法、浅层元组解包、关联函数及布局 | 不支持递归绑定；按值直接递归拒绝；枚举当前布局未优化为 union |
| Copy、移动与 Drop | 显式 Copy、自定义非泛型 Drop、部分移动和所有正常退出清理 | 泛型条件 Copy/自定义 Drop、部分下标/指针资源原位替换尚未实现；panic 无栈展开保证 |
| 普通指针 | 取地址/解引用、写权限、外层降权、别名与风险 warning | 风险分析不完整且可能误报；不是 Rust 式生命期/独占证明 |
| 结果与分流 | T? / T?[E]、数字通道、单层命名分支、传播和 panic | E: Error 是可表达的目标能力约束，通用 Error Trait 尚不能运行 |
| 模式选择 | 枚举变体、标量字面量、通配、穷尽检查与指针匹配 | 已规定的组合、元组选择和负载过滤尚未实现；嵌套模式明确不支持 |
| 泛型 | 函数/结构体/枚举/固有方法的具体实例，推导及 Copy 约束 | 通用 Trait 分派、泛型 Copy/Drop、编译期值参数未实现；未使用模板正文延迟检查 |
| 函数值与闭包 | 函数指针、无捕获 fn、显式环境、重复/可写/一次调用 | 不同捕获类型不自动合并；无动态闭包共同类型、独立泛型闭包或公共 Call Trait |
| 迭代 | Array/Vec/Slice 指针遍历、范围、next/Step、from_fn、bytes/chars | yield 暂停恢复、通用迭代 Trait 和 iter_mut/into_iter 接口未实现 |
| 基础容器与文本 | String、UTF-8 str、Array、Slice/SliceMut、Vec、递归节点容器 | 无完整 Map/Set/Arena/哈希排序库；Vec/String 分配失败终止 |
| 堆对象与共同拥有 | Box/Shared/Weak、可失败创建、显式 share 和弱升级 | 普通指针不延长生命；Shared 强环不自动回收；无用户分配器 |
| 线程与同步 | POSIX Thread、Mutex/Guard、自动等待/解锁、失败清理 | 无完整 Send/Sync 证明、后台线程、异步或其他平台验收 |
| 模块与包 | 文件模块、pub/use、限定路径、重导出与本地 path 依赖 | 无注册表/Git 依赖、锁文件、模块缓存；标准接口主要由 C 和编译器支撑 |
| IO、参数与格式化 | print/println/eprintln/readline、args、文件读写/flush、format | 仅 `{}` / `{:p}`；无通用 Display/Debug、动态格式化、路径/目录/进程完整 API |
| ABI 与底层控制 | 类型化普通指针、定宽整数、内联数组、可观察的生成 C | extern 仅前端支持；地址整数化、布局/对齐/volatile 等不构成可用平台层 |
| 构建与工具 | AST/check/emit-c/build/run、结构化诊断、失败保护、audit | 没有官方 fmt/LSP、完整 Xe 源码调试映射、统一 xe 工具或自举 CI |

接口图示的 core/alloc/std/platform、HIR/MIR、.xmi、LLVM 和增量缓存是目标架构，
不是现有目录都已实现。当前路径是：可达模块 AST + 类型侧表 → 一个 C 翻译单元 → 系统 C 编译器。
这条简单路线适合首版自举，不需要先完成优化器、寄存器分配或专用机器码后端。

### 直接探测得到的能力诊断

除了阅读实现和测试，本轮用最小程序分别触发以下边界：

- 通用 Trait impl、组合/元组选择、负载筛选、泛型 Copy：`XE-SEM-0001`。
- extern、`println("{:?}", 1)`、`let N: i32 = 1 + 2;`（模块顶层）：`XE-BACKEND-0001`。
- 对 `Vec[Box[i32]]` / `Array[Box[i32], 1]` 的元素或 `Box[i32]@[mut]` 所指值用
  `<<` 替换，语义检查可通过，但后端的旧资源清理路径尚未实现，报告 `XE-BACKEND-0001`。
  拥有局部/字段替换与 String 指针替换有支持，不应把它们推广到所有索引/指针资源。
- 用户结构体即使实现 Copy，也不能直接据此获得 `==`；目前比较支持数值、bool、char、str。
- `.addr()`：名称/方法诊断；普通指针加整数：类型诊断；`&` 位操作：词法诊断。
- 历史 `unsafe { ... }` 外形仍能解析，但后端拒绝；不是当前普通指针操作的许可块。
- 未使用的泛型函数正文可以暂含未知名称；被实例化时才检查。
  这是延迟实例检查的已知策略，不应宣传为模板声明已获通用证明。
- `(object.f)(x)` 能生成 C，`object.f(x)` 不因 f 是函数字段而自动改作字段调用。

其中有些属于已规定但未完成的功能，有些只是历史保留或尚待设计的底层需求。
不能为了让探测通过擅自赋予新符号含义。

## 可读性与合理性的得失

### 已有优势

类型后置、地址运算、明确字段初始化和显式捕获便于读者追踪局部含义；
错误作为值，参数传递不特殊照顾输出函数，作用域清理覆盖正常控制流。
元组与块有不同入口，选择器与参数绑定分开，匿名函数与立即处理分开，
都解决了曾经需要靠逗号、函数值类型或“作者大概想什么”来判断的冲突。
JSON、源码范围、稳定错误代码及端到端测试给工具提供可靠接口，而不是另外发明 AI 专属语法。

### 仍需坦诚解释的成本

- `[]` 很醒目，但含义较多；教程应先讲左侧入口，再讲附件，而不是一次列完所有用法。
- 处理参数正文贪婪包含后续管道：`value |> x -> f(x) |> g` 中 g 在正文内，
  并不是外层的新步骤。连续步骤优先用命名处理函数或 `fn` 块，不能凭换行制造边界。
- `<<` 不能用于 Copy，`>>` 却可以；这是已批准的设计取舍，不是对称的数学代数。
  未知 T 的普通返回/实参与字段 >> 可避免到处按 Copy 分支编写泛型代码。
- 只读绑定、只读指针、对象内容不变是三件事。另一个可写别名仍可以改内容；
  Shared 的计数、Mutex 的锁以及 File 的流状态也不能简单解释成“只读方法没有副作用”。
- 方法、容器 for 和地址捕获有便利规则，但它们不是随意改类型。需要短小对照示例，
  并在诊断里说清楚原类型、输入类型和访问权限。
- `String??[io::Error]` 合理地区分 IO 失败与 EOF，但视觉较密；可以用已实现的 type 别名
  命名业务结果，不需要再添加自动展开或异常语法。
- 指针风险只 warning，降低静态证明负担，也把悬垂、失效与数据竞争责任留给程序员。
  教学时不能把“能编译”教成“不会发生内存问题”。

### 尚需用户决定的语义边界

1. **只读接收者和外部状态。** File.read_to_string 通过 File@ 推进游标；
   Shared.share 修改计数；Mutex.lock 获取锁并返回 Guard。这些操作都有副作用。
   已确认的 Shared/Mutex 契约不变；File 是否也明确采用“对象描述符只读、外部状态可变”，
   或要求可写 self，仍需用户决定。禁止据此偷偷改签名。
2. **可恢复失败是否统一。** Box/Shared 创建返回分配结果，Vec/String 失败终止；
   字符串切片返回可选值，数组切片越界终止，File.size 不可 seek 时终止。
   建议提供一致的可恢复基础接口及明确的 panic 便利入口，但具体接口需审核。
3. **线程失败范围。** spawn 的创建失败返回结果；join 在有效 POSIX 句柄下正常返回 Yes，
   自等待/异常系统失败目前终止，子线程 panic 也终止进程。是否扩展可恢复线程错误另行决定。
   Thread 自动 drop 会阻塞等待，不能只把它介绍为“方便回收”而不说明死锁可能性。
4. **底层能力的风格。** FFI、布局/对齐、位操作、地址运算和 volatile/原子接口还需补齐。
   建议先采用显式平台函数/现有附件风格，不让所有权 << / >> 同时悄悄变成数字移位。
5. **Trait 与模式扩展。** 已有静态 Trait 外形和一层模式规则可以保持；
   应落实其检查/分派与剩余选择器语义，不以新语法掩盖旧语法尚不能运行的问题。

## 三个目标分别离多远

### OCaml 式的编译器开发体验

OCaml 的变体、记录和递归模式很适合表达语法树及多轮变换。
参考：[类型定义](https://ocaml.org/manual/5.4/typedecl.html)、
[模式](https://ocaml.org/manual/5.4/patterns.html)。
Xe 已有枚举、泛型容器、块表达式和管道，可表达同类业务结构。
但一层匹配需要更显式地逐层处理，资源管理也比 GC 模型多一些约定；
不能声称在所有编译器遍历上都同样简短。

建议首版使用 Vec 存储 Token/Node/Diagnostic，以稳定整数 ID 表示节点关系，
先用普通函数处理编译阶段。这样可避免树的每条边都需要指针或共享拥有，
也不立即要求动态 Trait、递归闭包或复杂生命周期。
Map 可先用线性名称表替代，正确性不受影响；大项目的查找效率再按实际需要优化。

### 比 Rust 更容易理解

Rust 的引用规则提供重要静态约束，包括共享与可写引用的限制。
参考：[引用与借用](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)。
Xe 不要求独占别名证明，T@ 就是普通指针；明确捕获和资源传递也能减少一些猜测。
这是“少学某些概念”的可解释优势，不是得到相同安全保证之后的全面简化。
需要用新手阅读/修改任务实际测量理解率，而不能凭符号更短得出普遍优越结论。

### C/C++ 式的底层能力

已有定宽数值、普通指针、可写别名、内联数组、显式堆拥有和确定性资源清理。
但是可运行 C 后端不等于 Xe 用户已经能调用所有 C 接口或编写操作系统。
extern ABI、布局/对齐、位操作、硬件相关访问、平台和裸机构建仍不是闭环。
“足够底层”要用具体 C 库绑定或系统模块验收，不能只用生成 C 作为证据。

## 自举：现在可以开始，尚未完成

自举不是“有足够多的语言功能”，而是本语言编译器真的能编译自身。
成熟工具链也使用分阶段构建验证这条链。
参考：[Rust 的 bootstrap 阶段](https://rustc-dev-guide.rust-lang.org/building/bootstrapping/what-bootstrapping-does.html)。

### 不必再等待的能力

文本字节遍历、可增长节点表、记录/枚举、普通函数、泛型实例、文件输入输出、参数、
模块及 C 文本输出已经具备。用 Vec 和整数 ID 可以替代第一版 Arena/Map，
不使用通用 Trait 就能组织一个维护性良好的最小编译器。
yield、异步、复杂模式、动态闭包、多线程、LLVM 和 HIR/MIR 重构不是开工条件。
GC、原生机器码或完全 Xe 标准库也不是自举的定义要求。

### 真正缺少的成果

1. **Xe 编译器源码。** 现有 Calculator 是算术扫描/解析/求值示例，Source Scan 是位置扫描工具，
   都不是 Xe 语言的完整前端或代码生成器。需要把实际语言子集的 lexer/parser/checker/emitter 写出来。
2. **固定且双向覆盖的自举子集。** 不是“只会编译 hello”的玩具子集，必须覆盖新编译器自身
   用到的全部写法，并明确它暂不接受哪些规范。Python 和 Xe 实现运行同一组正反例。
3. **构建驱动选择。** Xe 当前没有公开子进程 API，不能独立启动 cc。
   可以先让 Xe 编译器读取源码并输出 C，由现有外部驱动调用系统 C 编译器；
   这可建立自编译链，但应标明驱动仍外置。是否补进程/FFI 接口需要单独审核实现。
4. **固定点与回归记录。** stage0 编译 Xe 编译器得到 stage1，stage1 编译同份源码得到 stage2，
   stage2 再构建 stage3；比较规范化 C/产物与成功、失败、诊断、资源行为，控制路径和时间戳影响。
   给出一条别人也能重复执行的命令和 CI 记录，而不是宣称理论上能够自举。

优先顺序建议：先让 Xe 前端输出可比对 AST → 加类型/资源检查与 C 发射 → 跑通阶段链，
期间只补真正阻塞编译器源码的库能力。通用 Trait 与高级优化可以并行规划，但不当成
必须先大幅重构才能做任何自举工作的理由。未实际移植与构建前不给工期或完成百分比。

## 代码可维护性与本轮验收

前端 AST 与类型侧表分离、普通指针风险与阻断错误分离、构建失败保护、成功/失败及
资源运行测试已经是良好基础。容器/线程/模块有独立文件，也有面向维护者的说明。
主语义文件约 2600 行、C 后端约 1900 行，仍承担很多功能；建议迁移时按名称/类型/
资源/调用/发射职责拆分，并保留不变量注释及小型交互测试，不重写无关解析算法。
当前显式清理选择存在二次复杂度路径，默认 C 构建为 -O0；还没有足以与成熟编译器
比较吞吐量、内存、生成代码性能的基准，不承诺“最优自举实现”。

本轮实际执行：

- 全套 772 项 unittest 通过，包含后端真实执行与 ASan/UBSan/资源清理测试；
- 最小能力探测核对前端通过但后端拒绝的边界，不把它们算成已经可用；
- `make audit` 审核 37 个 stage999 样例，全部通过 AST/语义/C/系统编译；
  36 个运行通过，1 个已有指针风险样例按策略跳过运行，没有为了全绿执行悬垂程序；
- Calculator、Source Scan、线程计数器、Feature Check 用现有 Makefile 构建运行；
  线程输出 `completed=2000 counter=2000`，Feature Check 的 16 组检查全部通过。

测试通过不证明所有合法组合无 bug，资源测试不证明普通指针程序完全安全，
应用示例不证明已自举。本章是可以追溯证据的阶段快照，能力变化后应更新。
