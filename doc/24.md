# 标准输入输出与 Xe 命令行示例

本章说明当前 stage0 标准库的 `print`、`println` 和 `readline`，以及用这些接口编写的
Xe 命令行功能展示工具。它们沿用现有类型、分支和所有权规则，没有增加语法符号；
当前语法版本为 `xe-1.0`；发布范围见第 38 章。

## 输出与所有权

`print` 写 stdout，不追加换行；`println` 追加一个换行。
简短名称和 `std::io::` 完整路径是同一个已登记接口：

```xe
fn main() {
    let text << String::from("hello");
    print("{}", text@);
    std::io::println(", {}", "Xe");
}
```

格式字符串仍须是编译期字符串字面量，占位符数量及参数类型在编译期检查。
`str` 是 Copy 视图，可以复制传入；`String` 是拥有资源，保留它时必须明确传 `text@`。
按值写 `println("{}", text)` 就会转交 text，之后不能继续使用；没有为输出增加隐式借用。
`eprintln` 使用同样的格式化和所有权规则，只是写入 stderr。
输出失败沿用 panic 合同；程序退出前也检查缓冲刷新，防止延迟写入错误被忽略。

## 为什么 readline 返回两个问号

一次读取面对两个独立的问题：读操作是否成功；成功后有没有读到一行。
因此类型写作 `String??[io::Error]`，先构造内层 `String?`，再给它增加外层 IO 错误通道。

| 结果 | 程序应如何理解 |
| --- | --- |
| 外层 Yes，内层 Yes[String] | 有一行，包括长度为零的空行 |
| 外层 Yes，内层 None | 正常 EOF，没有下一行 |
| 外层 No[io::Error] | 读取失败，例如输入错误或不合法的 UTF-8 |

若把三者都改为空字符串，程序就分不清用户按下了回车、输入已经结束还是读操作失败。
两个问号只是组合已有的结果类型，不要求新的空值约定或异常机制。
每次 `?` 仍只消解当前一层，先处理 IO 结果，再处理行/EOF：

```xe
fn main() -> i32 {
    let reading: String??[io::Error] << readline();
    reading ?
        1> maybe_line -> maybe_line ?
            1> line -> { println("{}", line@); 0 }
            2> _ -> { println("eof"); 0 }
        2> error -> { eprintln("read error: {}", error); 1 }
}
```

`reading` 含有拥有的 String，使用 `<<` 接收；匹配把 String 所有权交给被选分支。
分支中的 `line@` 只复制地址，输出后拥有的 line 仍按作用域规则清理。
选择 `?[panic]` 可以明确终止失败，但标准库本身不会把 EOF 或 IO 错误偷偷变成 panic。
`std::io::Error` 和 `io::Error` 是同一类型，可使用完整路径表达来源。

## 输入边界

`readline` 在等待 stdin 前刷新 stdout，因此 `print("command> ");` 的提示不会因缺少换行
留在缓冲区中。读取到 LF 时去掉 LF 和此前的 CR，兼容常见的 LF/CRLF 文本。
EOF 前没有换行的最后一行仍返回；只剩一个 CR 时不把它误当成 CRLF。

返回值是拥有的 UTF-8 String。输入中的 NUL 按长度保存，不会在第一个零字节截断。
不合法的 UTF-8 返回外层 IO 错误，失败不伪装成 EOF。输入结束后再次读仍可正常识别 EOF。

## 标准库实现与模块边界

实现位于 [stdlib/io/xe_io.h](../stdlib/io/xe_io.h)，这是当前可替换的 C 标准库部分，
不是用 Xe 编写的完整标准库。Python 检查器和 C 后端通过
`compiler/xe_ast/stdlib_io.py` 的已声明接口登记名称、参数与返回类型。
生成 C 保留独立构建能力，String 与资源清理沿用已有的小运行库。

`std::io::readline()` 的路径让接口来源明确，也可以 use std::io::readline 导入。
本地文件模块加载已完成（第 27 章）；这些 IO 名称仍由编译器登记，不是完整 Xe 源码
标准库或外部 ABI。完整标准库目标见第 13 章，当前目录状态见 [stdlib/README.md](../stdlib/README.md)。

`readline` 是固定签名的函数，也能作为函数值：

```xe
type Reader = fn() -> String??[std::io::Error];
fn read_with(reader: Reader) -> String??[io::Error] { reader() }
```

调用 `read_with(std::io::readline)` 与直接读取遵循相同的结果及资源规则。
print 系列的异构格式化仍需编译器协助，不是已经实现了通用可变参数 Trait；
目前只能直接调用，或包装为具有固定参数类型的具名函数/无捕获 fn。

## 终端识别、提示与颜色

标准库提供五个无参数、返回 bool 的查询函数：

```xe
std::io::stdin_is_terminal()
std::io::stdout_is_terminal()
std::io::stderr_is_terminal()
std::io::stdout_supports_color()
std::io::stderr_supports_color()
```

前三个查询相应流是否连接终端；后两个只在相应流是终端，且没有非空
`NO_COLOR`、`TERM` 不等于 `dumb` 时允许颜色。环境配置禁用颜色并不改变
流的终端身份。stdout 与 stderr 独立判断，不能因为其中一个是终端就给另一个
已重定向的流加上颜色。库只提供判断，不会自动给 print 或 eprintln 染色。

Feature Check 仅在 stdin 和 stdout 都是终端时显示 `xe> ` 和 `text> `。
提示仍是普通 print，readline 等待输入前的刷新保证用户先看到它；终端 EOF 后
工具补换行。管道输入不显示提示，重定向的输出不写入 ANSI 颜色；仅输入来自管道而
输出仍是终端时，输出依旧可以有颜色。终端上的标题与提示为青色，
通过项为绿色，失败项及错误为红色，使用后立即复位；echo 正文始终保持原样。
这是一种标准库支持的应用行为，不是新增的语言语法或 print 的特殊规则。

## 运行示例与验证

[tests/backend/readline.xe](../tests/backend/readline.xe) 循环输出每一行，区分空行和 EOF，
失败时写 stderr 并返回非零退出码。自动审核不提供 stdin 时，它打印 eof 后立即退出。

```sh
make run SOURCE=tests/backend/readline.xe
```

测试必须真正向可执行程序传入 stdin，检查 stdout、stderr、退出码与资源清理。
`test_stdlib_io.py` 覆盖输入边界并使用 ASan/UBSan；只比较生成的 C 文本不能证明
空行、EOF、NUL 或提示刷新行为正确。

命令行功能工具位于 [examples/feature_check](../examples/feature_check/README.md)，用 Xe 编写
help/check/echo/quit 命令循环，展示已有语言能力与标准库 IO。它是可执行的语言示例，
不是一个替代 Python stage0 的自举编译器，也不会接收任意源码并完成编译。

```sh
make feature-check  # 构建工具，并运行全部 16 组功能检查
make feature-run    # 构建工具，再交互输入 help/check/echo/quit
make stdlib-test    # IO 语义、真实输入输出、内存清理和工具错误路径
```

只需构建时使用 `make feature-tool`，得到 `target/debug/xe-feature-check`。
工具无参数时的输入来自 stdin，用管道也可以自动验证。
现在还可以直接传入 `check`、`echo "你好 Xe"` 或 `--help`；
标准库参数接口及最小打印工具见 [第 25 章](25.md)，没有新增语言语法。
交互时未知命令只提醒并继续；若此前没有检查失败，quit 或 EOF 正常返回 0。
检查失败的状态会保留，IO 失败仍退出 3。参数模式的未知命令或多余参数退出 2。
真实 PTY 回归测试覆盖提示刷新、颜色开关、未知命令后的继续运行及独立重定向。
