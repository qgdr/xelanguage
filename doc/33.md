# Xe 1.0：编译器核心还缺什么

审核日期：2026-10-02。本文核对当前 Python stage0、C 后端、自举子集、冻结规范与测试。
本章保留 1.0 核心补全与发布建议的来由；本轮发布收尾的实际候选契约见
[第 38 章](38.md) 和 [RELEASE](../RELEASE.md)，不要将下文建议当作当前仍全部缺失。
这里只列编译器必须参与的能力；Map/Set、排序、网络包装、文件便利等普通模块可实现的
功能不计入缺口。建议不是新增语法规定；尚未确认的规则仍要先讨论。

## 结论与发布范围

Xe 已能编译、运行多文件程序，支持结构体/枚举、泛型具体实例、显式资源管理、闭包、
迭代、普通指针和静态 Copy 全局变量。统一工具链与一个可自编译的 Xe 子集也已存在。
这是一门可用于试验和实际小项目的早期语言，但现在不能把完整现有规范称为成熟 1.0。

1.0 不等于实现 Rust/OCaml 的所有功能，也不等于必须自己实现优化器、机器码或 GC。
发布门槛应是：清楚公布支持范围，范围内的有效程序能正确生成可执行代码，无效程序有
稳定诊断，已经承诺的类型/权限/所有权规则不会在组合使用时改变。

有限 C FFI 已按用户确认接入，平台包装不再只能依赖编译器的内建函数白名单。
但当前只承诺标量/指针等明确 ABI；这不等于所有原生接口或裸机能力已经完成。

## 本轮已补齐的既定核心

| 项目 | 当前实现 | 明确保留的边界 |
| --- | --- | --- |
| 静态 Trait | 契约签名、默认方法、泛型约束、具体实例直接调用 | 动态对象、关联类型、父 Trait、重叠特化不支持；同类型族同名方法拒绝消歧猜测 |
| 泛型 Copy/Drop | 条件 Copy 按具体实例判断；具体 Drop 先检查再生成，递归字段正常清理 | 泛型正文仍按实例需要检查；不承诺完整声明级多态证明 |
| 一层模式选择 | 元组、组合、变体直接负载过滤、覆盖与不可达诊断 | 不递归展开；选择器不绑定，参数只在 :> 后声明 |
| 资源原位替换 | 局部、字段、Array/Vec/切片及可写指针统一保存新值、清理旧值、移入新值 | 普通指针仍须由用户保证地址有效，不授予移出资源权限 |
| 静态数据与数值 | 模块只读/可写静态存储、已有标量字面量运算、数值范围检查 | 动态函数/块初值与资源全局拒绝；浮点 % 在检查阶段拒绝 |
| 有限 C FFI | extern C 标量/指针、void/Unit 桥接、兼容回调、显式链接 C/.o/库 | 聚合 ABI、可变参数、其他调用约定与 C 导出库不支持 |
| 单词位操作 | bitand/bitor/bitxor/bitnot/bitshl/bitshr；次数与左移溢出检查 | 不提供传统符号，不复用所有权 << / >>，不因此承诺裸机能力 |

这些能力都有实际编译运行及反例测试；规则与维护入口分别见第 34—37 章。
测试包含普通指针/数组/Vec 的资源替换、Trait handler 与泛型 Drop 组合、真实 C 链接，
并保留 sanitizer 默认泄漏检测。测试通过不是“所有程序都正确”的证明。

## 底层语言还需要编译器提供的入口

### C FFI 与 ABI

`extern "C"` 已能检查、发射与链接。后续扩展仍需要逐项审核：

1. C 可用聚合的布局/对齐与公开符号约定；
2. C 导出库、其他 ABI 和可变参数；
3. 空指针、视图、资源及外部分配失败的包装边界。

不能直接把 Xe `T?` 当作 C 的 NULL 指针 ABI；现在的 malloc 例子是目标包装说明，
不是已经可运行的外部签名。以上接口要先明确约定，不靠后端猜测。

### 地址、布局和机器操作

目前尚无完整的布局/对齐控制、大小查询、地址整数转换、指针偏移、volatile 和原子访问
契约。数值位操作/受检查移位已实现。普通模块可以提供方便封装，但它必须
建立在编译器或 FFI 能表达相应机器操作的基础上。

若 1.0 只针对应用开发，这些可以明确延期；若承诺可做操作系统/硬件层，就属于必要
平台核心。不要为方便实现把所有权 `<<` / `>>` 再解释成整数移位，不擅自增加符号。
完整裸机、所有平台 ABI 和所有原子能力不必一次完成；先明确一种可验收的平台范围。

## 已确认与仍需确认的规则边界

### 模块只读值与全局对象

按用户确认，模块 `let` 与 `let[mut]` 都有真正的静态存储，差别只有写权限。
两者支持静态字段/数组、跨函数/模块访问和稳定地址。

```xe
let LIMIT: i32 = 10;        // LIMIT@ 合法；LIMIT@[mut] 报错
let[mut] count: i32 = 0;    // 当前是静态对象，count@ / count@[mut] 可用
```

编译器仍可内部折叠只读值，但不能把可观察的对象地址换成临时副本地址，不需要重新
引入 const 关键字。AST Constant 仅为工具兼容的节点名称。

当前全局仅支持静态 Copy 数据。资源全局、运行时初始化、失败行为和退出时 Drop 需要
先确定初始化/清理顺序；若 1.0 明确不提供它们，可以延期，不是必然发布阻塞。
全局变量也不自动线程安全；可写指针不是锁。

### 泛型什么时候检查

当前策略是具体实例化后检查正文；未使用的泛型函数可以暂含未知名称。这是既有测试
明确固定的策略，不宜直接当成编译器 bug。

1.0 需要说明 `xe check` 证明的是“已实例化程序”，还是包括所有泛型声明。建议即使保留
实例化策略，也尽量在声明时检查不依赖未知类型的名称、语法和控制流错误；完整约束下
的泛型正文检查需要随 Trait 系统一起完善，而不是把未知类型当成万能通行证。

## 发布可靠性也属于编译器自身

当前已经有 AST/check/emit-c/build/run/test、JSON 诊断、失败保护、产物缓存、安全 clean、
保守 fmt 和 API 文档工具，不能把这些全部列为缺失。真实执行、sanitizer 和自举固定点
测试也已存在。

1.0 建议补的是：

- 对发布范围内的每项功能同时验收解析、检查、生成 C 和实际执行，并测试组合情况；
  unsupported 可以明确存在，但不应让“规范有效、当前尚未实现”和“语言本身非法”混淆。
- 支持范围/错误代码/ABI/行为规则版本化，加入自动化发布验收；候选版现已有
  `make release-check` 和 Linux GitHub Actions 配置，远程结果需在提交后核对。
- 让基础运行时错误与调试定位 Xe 源码。已有 `-g` 主要给生成 C 提供调试信息，尚无完整
  Xe 源码映射；候选版已加基础运行时文件/行/列定位，不是完整调试器、栈回溯或
  LSP。多错误恢复可以后推。
- 明确验收平台。当前线程依赖 POSIX，C 工具面向 GCC/Clang；先支持明确的 Linux 配置
  也是合法 1.0 方案，不必宣称所有操作系统都已支持。

## 不列入这次 1.0 必补清单

普通集合/哈希/排序/网络/目录/进程包装等库功能按本次讨论范围排除。C FFI 是让这些
库能脱离编译器内建白名单的底座，不能因为“它们都是库”就连 FFI 一起忽略。

yield 状态机、async、动态闭包共同类型、独立泛型闭包、动态 Trait 对象、嵌套模式和
守卫、常量泛型、复杂优化、LLVM/直接机器码、完整 LSP、增量编译、全语言自举可以继续
延期。基础闭包、`next() -> Step[T]` 迭代与静态具体泛型已经可用，不能重复当作未实现。
Rust 式生命周期/独占借用证明也不是当前普通指针设计的目标，不重新列为必补项。

## 建议的实现顺序

上述核心补全后，1.0 下一步更应关注发布契约，而不是无限扩充语法：

1. 固定支持的平台、ABI、错误代码和已实现的语法/组合范围；
2. 逐项清理剩余 check/build 诊断差异，增加真实应用回归；
3. 加入自动发布验收与基础 Xe 源码定位；
4. 审核并按需求补底层入口，不把嵌入式目标当作当前保证；
5. 再决定 1.0 发布范围；完整自举仍为独立项目。
